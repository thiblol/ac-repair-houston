## What this site is

A static, zero-runtime-dependency website generated from JSON data. All copy
lives in `data/copy/`, all structure lives in `src/`, and the build writes
static HTML to `dist/`.

The architecture is deliberately not a framework. A site with a few hundred
pages of location copy needs to build in seconds, deploy to any static host,
and be editable by someone who does not want to learn React.

```
data/
  config.json        brand, domain, positioning, disclosure, conversion state
  services.json      the 21 AC services, one of which is the pillar (ac-repair)
  areas.json         Houston as the pillar area, 16 Houston neighborhoods,
                     24 Greater Houston municipalities, each with real traits
  copy/              one JSON file per page group, all prose written per page
src/
  build.mjs          the generator and every build gate
  links.mjs          the URL map, the proximity model, the link graph audit
  templates.mjs      page structure only, no prose, no invented claims
  check.mjs          source and data checks
  audit-copy.mjs     shingle similarity audit, the doorway-page gate
  build-images.mjs   renders src/svg/*.svg and src/img/*.jpg to responsive WebP
  svg/               the original labelled illustrations
  img/               the photographs
public/              static assets copied verbatim into dist/
dist/                build output, not committed
```

## The taxonomy

The pillar service is **AC repair**. The pillar area is **Houston**. Everything
else hangs off those two, and the links between them are generated in one
place (`src/links.mjs`) so the graph is auditable rather than emergent.

```
/                                    home
/services/                           all services
/services/{service}/                 20 service pages, location neutral
/service-areas/                      all areas
/service-areas/houston-tx/           PILLAR AREA, all 20 services
/service-areas/houston-tx/{service}/ Houston x service, 20 pages
/service-areas/houston-tx/neighborhoods/{name}/  16 Houston neighborhoods
/service-areas/{city}/               24 Greater Houston municipalities
/service-areas/{city}/{service}/     14 services per city, 336 pages
/how-it-works/  /for-hvac-companies/  /privacy/  /terms/  /sitemap/
```

Every area page links to every service that covers it. Every service page links
to every area that carries it. Every area links to its six nearest neighbours
by real haversine distance. Every area x service page links to the same
service in nearby areas and to its sibling services. The build fails on an
orphan page or a dangling link, so the graph cannot rot.

### Why cities get fourteen services and Houston gets twenty

Twenty services across twenty-five areas is 500 pages, and near-identical
pages are what Google reads as a doorway network. Houston is the pillar market
and carries the full set. Every other area carries the fourteen services that
a live search shows have dedicated pages of their own: emergency repair,
not-cooling diagnostics, repair, installation, replacement, maintenance,
condenser, compressor, refrigerant leak, refrigerant recharge, evaporator coil,
blower motor, thermostat and heat pump. The remaining six services still have
a full national page, and every area links to all of them.

## Build

- Runtime and version: Node 18 or newer. Developed on Node 26.
- Package manager: npm
- Install command: `npm install`
- Development command: `npm run dev` (builds, then serves `dist/` on
  `http://localhost:4173` via `npx http-server`)
- Production build command: `npm run build`
- Output directory: `dist/`
- Full check: `npm test` (source checks, copy audit, clean build, SEO audit, link audit)
- Copy audit: `npm run audit:copy`
- Page by page SEO audit of the built site: `npm run audit:seo`
- Internal link architecture audit: `npm run audit:links`

`sharp` is the only dependency and it is a build-time-only dependency: it
renders the illustrations and the photographs to WebP. It is not required to
serve the site or to run the generator against already-rendered images.

### Environment variables

| Name | Purpose |
| --- | --- |
| `STAGING` | When set to any value, every page gets `noindex,nofollow` and the staging banner appears. Leave unset in production. |

No secrets are involved at build time. The lead handler holds the secrets, and
it lives with the host, not in this repository.

## Deployment

- Recommended host: Cloudflare Pages, Netlify, or any static host that can run
  a small serverless function for the lead handler.
- Steps: `npm run build`, then upload `dist/` as the publish directory.
- Lead handler: `POST /api/leads`, deployed alongside the static site. The
  path is set in `data/config.json` under `conversion.endpoint`.
- Redirects and rewrites: none required. The site uses directory-style URLs
  (`/services/ac-repair/` served as `services/ac-repair/index.html`), which
  every static host handles by default.
- Custom headers: none required. If the host supports them, set
  `Cache-Control` for `/assets/*` and `/img/*` to a long max-age and
  `no-cache` for HTML.
- Domain and DNS: see `docs/LAUNCH-BLOCKERS.md` item 1.

## Lead routing

- Phone status: **one call tracking line**, configured in `data/config.json`
  under `phone`. It is published in the header, the ribbon, the fixed mobile
  bar, the request form and the `Organization` schema. It forwards to a
  partner company. The current value is a placeholder and the build prints a
  launch blocker until `phone.verified` is `true`.
- Form destination: `POST /api/leads`, status `"pending"` until the handler
  is deployed.
- Spam protection: a honeypot field on the form, plus rate limiting and a
  spam filter to be added to the handler before launch.
- Success and error behaviour: handled in `public/assets/main.js`. The form
  shows a sending state, a success message, and an error message that asks the
  user to try again. It never reports success for a failed submission.

**Why one number and why it is gated:** the number is owned by this site even
though a contractor answers it, so publishing it is honest, and it is the single
highest-value element on a mobile page for a service business. Two flags
control it. `phone.publish` decides whether a call button exists at all, and
`phone.verified` decides whether the number is real. The build refuses to
accept any phone number in the HTML that is not the one in the config, and it
refuses to let a placeholder be marked verified, so the placeholder cannot
reach production by accident.

## SEO and analytics

- Address status: none. There is no address, because there is no premises.
- Address published in content or schema: **No**, and it is not eligible.
- Google Business Profile: **not eligible**. A lead-generation property with
  no operator is ineligible under Google's service-area business rules. No
  profile has been created, claimed, or implied.
- Canonical domain: `cfg.origin` in `data/config.json`. Currently the
  `.example` placeholder.
- Sitemap: `/sitemap.xml`, generated at build time from the real page list.
- Robots: `/robots.txt` allows everything and points at the sitemap.
- Structured data types: `Organization`, `Service`, `WebSite`, `FAQPage`,
  `BreadcrumbList`. No `LocalBusiness`, no address, no `geo`, no
  `aggregateRating`, no review markup. The `Organization` carries the
  published call tracking number as its `contactPoint.telephone`.
- Analytics: not installed. See `docs/LAUNCH-BLOCKERS.md` item 5.
- Search Console owner: not set up.

## Known limitations

- **Photography is partial.** Four photographs and three labelled diagrams. The
  photographs cover the home hero, the area pages and the urgency service
  pages, which is where they earn their weight. The diagrams carry the
  technical sections, where a photograph teaches less than a labelled
  drawing does. One file serves many pages, so pages that share an image
  share its file name too; `docs/IMAGE-AUDIT.md` lists every conflict and
  the name each replacement should take.
- **The phone number is still a placeholder.** The call button is built and
  wired everywhere it should be, but `data/config.json` carries
  `(713) 555-0100` until the real call tracking line is bought. The build
  prints a launch blocker while `phone.verified` is `false`, and it fails if
  the number is marked verified while it still looks like a placeholder. Item
  3 in the launch blockers covers the swap.
- **Six services per non-Houston area.** The other fifteen services have
  national pages and are linked from every area, but do not get their own
  area x service page outside Houston. This is a deliberate anti-doorway
  decision, not an oversight.
- **No API or CMS.** Copy is edited by editing JSON files and running the
  build. That is the right trade at this size, but it means copy changes need
  a developer or a build pipeline.
- **The site is not deployed.** Deployment was not part of this task and no
  host has been chosen.
